# 네이버 예약 오픈 안정성 개선 검증

작성일: 2026-09-07. 기준 소스: v6.82, `57059be4a0cfd8f4755e454674a0c3f62ce13a79`.
작업 브랜치: `codex/naver-opening-reliability`. 기존 v6.73 작업 폴더와 다른 작업의 미커밋 변경은 건드리지 않았다. 이 문서는 소스 변경 검증이며 배포·실예약 성공 증명은 아니다.

릴리스 통합: v6.83의 `fef718d` 변경을 보존하여 병합했고, 네이버 개선은 v6.84 / 시퀀스 `6840001` 릴리스에 포함한다. 최종 빌드 커밋·EXE 해시·공개 서명 검증은 별도 릴리스 검증 기록에 남긴다.

v6.84 커밋 전 검증: 전체 테스트 **1,618개 통과**, UI **9개 통과**. 실제 `MainWindow → EngineRegistry → BaseEngine` 워커 연결에서 정상 임시 선점·응답 유실 복구·미확인 차단·결제 완료 대조를 검증했다. 이 테스트의 브라우저·네트워크 경계는 대체되었으며 실예약을 실행하지 않았다.

## 실패 로그에서 확인되는 것

9월 7일 바야흐로 실행은 타이머 오차 +0.5ms, 초기 시계 불확실성 106ms, 최종 398~399ms, POST 1회, RT47/OUT_OF_STOCK, 본인 예약내역 미확인으로 끝났다. 표시된 서버 도착 -19.3ms는 RTT로 계산한 추정치다. 서버의 실제 수신·재고 잠금 시각은 로그에 없다.

카카오톡 받은 파일의 붐붐 실패에서는 초기 PC 대비 -50ms였지만, 최종 대기 로그가 가리키는 PC 기준 오픈 시각은 약 00:00:00.968이었다. 약 918ms의 기준 이동을 의심할 근거지만 PC 시계 자체가 정확했다는 증거는 아니다.

이전 성공/실패 비교에서는 응답 시각에서 RTT를 뺀 발사 추정이 약 796ms 차이 난다. 다른 시간 슬롯·경쟁 조건이므로 타이머 변경이 승패를 결정했다고 단정할 수 없다. 구버전의 성공도 Npay 결제 전 임시 선점이었다. 이전 분석은 `docs/NAVER_V678_ANALYSIS.md`에 남아 있다.

따라서 타이머를 더 촘촘히 만드는 것만으로 해결되지 않는다. 동기화 기준의 품질, 제출 직전 대기, 동시 실행 간섭, 제출 후 결과 확인을 함께 고쳐야 한다.

공유 조회의 기본 상한은 동일 데이터 폴더에서 0.2초 간격이다. 정상 시간표 조회만 150ms 캐시로 공유하며 계정 정보·CSRF·개인정보는 공유 캐시에 저장하지 않는다. 최종 예약 POST는 공개 조회 대기열을 거치지 않는다.

제출 보호 기록은 해시로 저장된다. `NOT_OPEN`만 확실하고 상충하는 오류나 부분 URL이 없거나, 브라우저 타이머가 발사 전 취소됐다는 확인이 있어야 재시도할 수 있다. RT47·응답 유실·중복 응답은 읽기로 대조한다. 프로세스가 죽었다고 미확정 제출 기록을 자동 해제하지 않는다. 같은 프로필에서 계정을 바꾸더라도 같은 대상의 미확정 기록이 있으면 보수적으로 차단한다.

## 결과 확인 근거

공식 프런트엔드의 [`main.696e1655.js`](https://m.booking.naver.com/mobile/static/js/main.696e1655.js)와 [`Booked-Check-Bridge.e6541d8e.chunk.js`](https://m.booking.naver.com/mobile/static/js/Booked-Check-Bridge.e6541d8e.chunk.js)에서 `bookingDetails(input: {bookingId, lang})`, 예약 RC02/RC03, 결제 CT01/CT02를 확인했다. 이것은 프런트엔드 사용 근거이며 서버의 결제 원자성이나 모든 상품 지원 보장은 아니다.

예약번호 없는 Npay `orderId`를 예약번호로 변환하는 공식 조회 API는 확인하지 못했다. URL의 공식 상세 경로나 `rurl`에 예약번호가 있는 경우만 후보를 추출한다. 현재 계정 ID를 확보하지 못하거나 상세 조회가 실패하면 자동 결제나 최종 성공 판정을 하지 않는다. `isMask=0`만으로 소유권을 증명하지 않는다.

## 검증과 남은 한계

오프라인 회귀 테스트는 실제 배포 JavaScript를 가상 시계·fetch로 실행하는 제출 테스트, Windows 프로세스 간 파일 잠금 경쟁, 시간 제한, 계정 전환, 클릭 응답 유실, 결제 상태 대조를 포함한다. 실제 예약·임시 점유·결제 요청은 실행하지 않았다.

최종 전체 `python -B -X utf8 -m pytest tests -q -p no:cacheprovider`: **1,590개 통과**(21.06초). 공유 모듈 43개 통과, Windows 프로세스 경합 3개 테스트를 3회 추가 반복하여 모두 통과했다. `git diff --check` 통과. 네이버 외 시간표 조회 테스트의 시간 제한 기대값 한 곳은 새 남은 시간 계산에 맞게 조정했다. UI 실행·배포 EXE 빌드·실서버 예약 성공률은 이 검증에 포함하지 않는다.

Windows 잠금 파일 초기화 중 일시적 `PermissionError`는 획득 단계에서만 재시도한다. 보호된 본문이나 잠금 해제 오류는 재실행하지 않는다. 공용 잠금의 최소 대기시간 때문에 호출 자체의 엄격한 100ms 종료는 보장하지 않으며, 예산이 지난 뒤 획득된 잠금은 본문 진입 없이 해제한다.

신규 진단 로그는 실행 식별자, 원시 시각 표본, 기준 이동의 후보/적용값, 타이머·ResourceTiming·탭 표시 상태, 재고 관측의 요청 시각 및 제출/응답/추정 오픈 대비 경과 시간을 기록한다. CSRF·쿠키·전체 예약 응답·결제 URL은 진단 필드에 넣지 않는다. 관측 재고는 서버가 처리한 순간의 잠금 내역을 뜻하지 않는다.

경쟁자 도착 시각, 서버 대기열·재고 처리, 결제 인증, 사용자 네트워크 편향은 제어하지 못한다. ±100ms 제한도 실제 오픈 시각 오차 보장이 아니다. 실제 서버 시계가 최종 구간에서 크게 변하면 이전 기준 유지가 불리할 수 있다. 다음 실제 오픈에서는 새 로그의 기준 이동·발사·조회 상태와 실제 예약/결제 결과를 함께 대조해야 한다. 이 변경만으로 99% 성공 또는 다음 예약 성공을 보장하지 않는다.

현재 실행 중인 기존 EXE에는 소스 변경만으로 적용되지 않는다. v6.84 업데이트를 설치해야 반영되며, 실제 예약 성공률은 별도 실전 검증이 필요하다.
