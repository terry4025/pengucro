# CGV v6.82: 최종 엔진 복구와 미오픈 선점 대기 보강

v6.81 재검토에서 재현한 실패 경로를 수정한다. 이번 변경은 PR #28의 모든 변경을 포함하며 네이버·단편선의 앞선 변경을 보존한다. 소스 PR과 Git 패치 제공이며 EXE/자동 업데이트 배포는 아니다.

## 수정한 결함과 동작

| 항목 | v6.81의 문제 | v6.82 동작 |
| --- | --- | --- |
| 성공 응답 복구 | 최종 Guard가 상태 읽기 실패를 `monitor-state-lost`로 바꿔 기본 엔진의 복구 분기를 건너뜀 | 이 상태도 동일 실행의 성공 응답 확인을 먼저 수행. 회차·좌석·가격 성공·선점 성공·임시 예매번호를 검증하고 기존 선점으로 연결. 증거가 없으면 추가 예약 없이 중단 |
| 늦게 수집한 회차 응답 | 이미 완료돼 있어도 6초가 지나면 먼저 취소하여 정상 응답과 429도 유실 | 완료 결과를 먼저 읽고 아직 진행 중인 조회에만 대기 한도 적용. 정상 결과는 후보에 반영하고 401·403·429는 추가 자동 선점 중단에 반영 |
| 좌석 조회 정지 | 좌석 조회가 반환하는 Promise와 브라우저 타이머를 기다림 | GET을 시작하고 상태를 수집하는 방식으로 바꿔 PC 시계로 2초 대기 확인. 종료 시 해당 GET 정리 |
| 가격·선점 응답 정지 | 8초 브라우저 타이머가 지연되면 다음 시간대 순환도 멈춤 | PC 시계로 진행 상태를 확인하고 가격·선점 합계 대기 한도 보강. Chrome 내부에서 실제 발송 여부를 확인한 뒤 처리 |
| 중단 직후 늦은 가격 응답 | 응답과 중단이 엇갈릴 수 있음 | 중단 여부와 AbortSignal을 가격 완료 후 다시 확인. 중단된 가격 응답으로 새 선점 POST를 발송하지 않음 |
| 거래 중 새 회차 | 후보 처리 경계에서만 별도 회차 감시 결과 수집 | 좌석 조회·가격·선점 대기 중에도 250ms 간격으로 감시 작업 점검. HTTP 회차 요청은 기존 시작 간격 목표 1초·최대 1개 유지 |
| 영화 ID 부분 공개 | 저장된 영화 ID가 있는데도 가격 요청에 빈 movNo를 넣는 경로 | 영화·포맷 및 명시적 ID 충돌 검사 후 검증된 목표 영화 ID만 보완. 실제·검증된 ID가 모두 없으면 가격 요청 없이 공개 완성 대기 |
| 반복 인증 조회 | 같은 후보에서 좌석 조회·응답 시드·선점 준비마다 인증정보 읽기 | 동일 페이지·회차, 최대 1초 안에서 인증정보만 공유. 선점 준비가 소비하면 폐기. 페이지·회차 변경, 만료, 실행 종료 시 재사용하지 않음 |

## 대기 한도에서의 판단

Python이 마지막으로 읽은 화면 상태만으로 선점 발송 여부를 판단하지 않는다. Chrome에서 같은 실행 ID의 상태 확인과 중단을 한 번의 실행으로 처리한다.

- 성공 응답이 이미 있으면 해당 결과를 우선 처리한다.
- 아직 선점 POST를 보내지 않았으면 현재 시도를 중단한다. 우선순위 엔진은 이 결과를 좌석 경합으로 오분류하지 않고 다음 희망 시간으로 이동한다.
- 이미 공개된 단일 회차의 기본 감시는 바깥 우선순위 순환이 없으므로, 선점 미발송이 확인된 대기 초과에만 1초 후 새 좌석표로 감시를 재개한다. 발송 후 결과 불명확에는 적용하지 않는다.
- 선점 POST를 보냈는데 결과가 불명확하면 성공 응답을 최대 1초 동안 추가 확인한다. 확인되지 않으면 추가 선점 없이 멈춘다.
- 별도 회차 감시에서 접근 제한이 확인됐더라도 이미 발송 중인 선점은 결과를 기다린다. 선점 발송 전이라면 원자적으로 중단하여 제한 확인 후 새 선점이 나가지 않게 한다.

2초·8초는 정상적인 Chrome/CDP 응답이 가능한 상태에서 PC 시계로 점검하는 대기 기준이다. 개별 CDP 호출 자체의 정지, OS 절전, 프로세스 종료까지 강제로 끊는 별도 프로세스 감시기는 아니다. 전체 연결이 완전히 정지하면 복구 시간 상한을 보장하지 않는다.

좌석 선점 요청 수를 늘리거나 여러 선점을 병렬 발송하지 않는다. 취소한 GET/가격 요청의 결과를 다시 받더라도 새 선점으로 이어지지 않도록 검증한다.

## 검증 결과

CGV·네이버·패치노트·업데이트 부트스트랩 **666개 통과, Windows 환경 의존 2개 제외**. 이번 버전 재현 테스트 29개를 포함한다.

이번에는 개별 기본 클래스만 검사하지 않고 `EngineRegistry`가 반환하는 최종 엔진에서 다음을 확인했다.

- 단일 시간 경로와 미오픈 우선순위 경로 모두 Guard의 상태 읽기 실패 → 성공 응답 검증 → 기존 선점 연결. 새 감시 설치 1회와 결제 화면 연결 1회 유지.
- 성공 조건이 맞지 않는 응답은 화면 재예약으로 넘기지 않고 결과 불명확으로 정지.
- 결과 불명확 상태가 남아 있어도 복구 예산 안에서 뒤늦게 보존된 성공 응답 확인.
- 6.1초 뒤 수집한 완료 응답에서 정상 회차 및 401·403·429 보존.
- Chrome 타이머 완료 신호가 없는 가격·선점·좌석 대기에서 PC 시계의 한도 처리. 선점 전 대기 초과 후 다음 시간대 이동.
- 실제 배포 JavaScript를 Node와 가짜 fetch로 실행. 가격 중단 후 늦은 응답에서도 hold 0회. 선점 발송 직후 중단 판단은 결과 불명확으로 분류하고 hold 1회 유지. 이미 보낸 요청의 늦은 성공 응답 보존.
- 좌석 조회 중 제한이 확인되면 감시 설치/선점 진행 없음.
- 동일 후보의 인증 조회 3회 경로를 1회로 줄임. 만료·페이지 변경 시 재조회.
- 알려진 영화 ID 보완, 다른 영화 ID 거부, 식별 불가 상태에서 대기, 원본 회차 응답 불변.

검증 명령:

```bash
python -m pytest -q tests/test_cgv*.py tests/test_naver*.py tests/test_patch_notes.py tests/test_update_bootstrap.py -k 'not test_cgv_engine_enter_naver_pay_password_success and not test_cgv_npay_password_persistence_and_reservation_data'
```

제외한 두 테스트는 개인 Windows 키패드 이미지와 Windows 보안 저장소에 의존한다. 이전 기준 버전에서도 같은 환경 실패를 재현했으며 통과로 계산하지 않는다.

가상 응답·시계·Node 검증은 실제 CGV 개방 순간의 선점 성공률이나 Windows 장시간 최소화 시험을 대체하지 않는다. 이 환경에는 실행 가능한 Chromium 설치가 없어 실제 브라우저 검증을 수행하지 못했다. Windows GUI·패치노트 버튼·EXE 빌드·로그인 만료·실제 좌석 선점·결제는 미검증이다.

## 실사용 및 남은 범위

- 이전 v6.81의 기본 `희망 시간 정확히 일치`를 유지한다. 참고 시간과 다른 실제 시간도 허용하려면 선택창에서 허용 범위를 명시적으로 저장한다.
- `빠른 시간 순환 · 약 3초`도 진행 중인 거래를 무조건 3초에 끊는 설정은 아니다. 이번 변경은 거래 대기 자체의 별도 한도를 보강한다.
- 서버가 응답 자체를 보내지 않아 본인 선점 여부를 확인할 수 없는 경우의 예매내역 자동 대조는 여전히 미구현이다. 검증된 CGV 본인 임시선점 조회 계약 없이 API를 추측하지 않는다.
- 임시선점은 결제 완료가 아니다. 성공 응답은 확인됐지만 화면 연결이 실패하면 기존 v6.81처럼 좌석을 유지하고 만료 전 수동 확인을 안내한다.
- 다음 실사용에서는 시작 로그의 버전·release sequence와 오픈 직전부터 결과까지의 로그를 함께 보관한다. 서버 실제 개방 시각, 요청 도착 순위, 경쟁자보다 얼마나 빨랐는지는 현재 로그만으로 확정할 수 없다.
