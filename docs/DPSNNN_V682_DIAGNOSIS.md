# 단편선 v6.82: 주문 실패 진단과 요청 제어

## 관측 범위 (2026-09-07 KST)

- v6.79의 9월 7일 자정 실행: 1프로그램 32작업. 주문 POST 10건은 HTTP 200이지만 엔진의 성공 조건을 충족하지 않았다. 첫 주문 실패는 23:59:59.711, 첫 마감 판정은 00:00:09.896, 첫 404는 00:00:59.470, 첫 429는 00:01:05.751이다.
- 따라서 후반 요청 제한은 확인되지만 최초 주문 실패의 원인이라고 단정할 수 없다. 당시 서버 메시지는 저장하지 않았으므로 과거 거절 사유를 복원했다고 주장하지 않는다.
- 24,778ms 샘플은 내부 허가 대기 24,769ms와 HTTP 8ms였다. DB 잠금과 작업 이탈은 없었다. 정상 중지는 40ms였다.
- 공식 예약 페이지 https://www.dpsnnn.com/reserve_g 에는 매진 상태가 캘린더에 늦게 반영될 수 있다는 안내가 있다. 직접 링크와 날짜 수정으로 접근할 때 중복 예약 문제가 생길 수 있으며 정상 접근을 우선한다는 안내도 확인했다.
- 브라우저에서 9월 13일을 선택해 목표 슬롯의 예약불가 상태와 9월 14일 미오픈 버튼 비활성화를 확인했다. 9월 8일의 실제 활성 카드로 진입한 상세 페이지는 `booking_f`의 기존 6개 필드 및 비회원 로그인 선택 후 주문 생성 구조를 유지했다. 날짜를 조작하거나 주문을 생성하지 않았다.
- 별도 일반 HTTP 조회는 403을 반환하여 추가 조회를 중단했다. 브라우저 조회와 HTTP 클라이언트의 결과 차이를 확인했을 뿐, 403을 우회하거나 해당 응답을 과거 실패 원인이라고 단정하지 않는다.

## 이번 변경

1. 감시 작업은 최대 32개를 유지하고 기본값은 4개로 조정했다. 기존 저장 설정은 보존한다. HTTP는 프로그램·호스트별 최대 8개/초당 8회로 분리하며, 오류 시 4→2→1 단계로 감속한다. 이는 보수적 정책값이지 실측 최적값이나 여러 창의 합산 안전 한도가 아니다.
2. Retry-After와 오류 대기를 지킨다. 오류 전에 출발한 요청의 늦은 200으로 감속을 해제하지 않는다. 정상 응답 16건과 15초 안정 시간을 모두 충족해야 한 단계 복구한다.
3. 주문 응답의 서버 메시지를 개인정보를 제거해 기록한다. 명확한 매진 응답만 재시도를 허용하며 프로그램 내부의 모든 작업에 최소 1초 주문 대기를 적용한다. 알 수 없는 메시지, 형식 오류, 성공 표시와 주문 코드 충돌은 기록을 유지하고 재전송 없이 중단한다.
4. 오래된 브라우저의 예약 가능 관측을 그대로 재사용하지 않는다. 401/403은 접근 상태 확인이 필요한 오류로 보고 자동 요청을 중단한다. 429 등 실패 응답은 정상 시간표 확인 시각을 갱신하지 않는다.
5. 주문 HTTP 로그에도 내부 허가 대기와 실제 HTTP 호출을 표시한다. 고정 40ms 재시도 문구로 실제 backoff를 오해하게 하던 오류 안내를 수정했다.

## 검증과 한계

- 실제 예약, 결제, 실서버 부하 테스트는 하지 않았다. 모의 응답의 회귀 테스트와 Windows spawn 프로세스 검증 결과는 릴리스 검증 기록에 별도로 남긴다.
- `submission_lock`, `_order_claimed`, 기존 `OrderJournal`의 응답 유실/재시작 중복 보호를 유지했다. 다른 목표의 프로그램들은 독립적으로 실행한다.
- 네 창을 사용한다면 우선 각 4작업을 권한다. 각 창의 요청량을 합치면 사이트/IP 제한을 초과할 수 있으므로, 이 설정도 성공률이나 무제한 확장성을 보장하지 않는다.
- 실제 오픈 순간의 서버 메시지와 경쟁 결과가 있어야 최초 실패 원인을 더 좁힐 수 있다. 슬롯 표시나 내부 주문 코드만으로 예약 접수를 성공 처리하지 않는다.
