# CGV v6.81 미오픈 감시·선점 유지 개선

v6.80에서 남아 있던 순차 회차 공개, 잔여석 집계 지연, 선점 후 화면 연결 실패를 보완한다. 이 문서는 소스 패치의 동작과 검증 범위를 설명한다. 실제 예약 성공이나 결제 완료를 보장하는 자료는 아니다.

## 변경 사항

| 문제 | v6.81 동작 |
| --- | --- |
| 좌석 탐색에 들어간 뒤 늦게 열린 회차를 한 바퀴 늦게 확인 | 같은 브라우저의 읽기 전용 회차 조회를 별도로 진행한다. 결과를 후보 탐색 경계에서 수집하고, 아직 방문하지 않은 희망 회차를 현재 순환에 반영한다. 첫 시간대부터 다시 시작하지 않는다. |
| 회차표의 잔여석 집계 0 때문에 실제 좌석 확인도 하지 않음 | 미오픈 실행에서는 회차 식별값이 완성되고 잠금이 해제된 경우 실제 좌석표를 제한 조회한다. 최신 좌석표에서 인원수와 좌석 우선순위가 맞아야 가격·선점 요청을 보낸다. 집계 0 자체를 판매 가능으로 판정하지 않는다. |
| 확보한 좌석을 화면 연결 실패 때문에 취소하고 재예약 | 동일 회차 화면 준비를 최대 2회 시도하고 기존 좌석 동기화 복구를 사용한다. 끝내 연결하지 못하면 임시선점을 유지하고 추가 자동 선점을 멈춘다. 결제 화면 클릭은 무작정 반복하지 않는다. 개발자 모드의 임시선점 해제는 유지한다. |
| 참고 날짜 시간에서 ±90분을 묵시적으로 허용 | 선택창에서 정확히 일치 / ±15·30·60·90분 허용을 선택한다. 기본값과 잘못된 저장값은 정확히 일치다. 선택창 → 예약 메타데이터 → 초기 감지 → 시간대 순환에 같은 범위를 적용한다. |
| 첫 회차 GET도 Chrome 타이머에 의존 | 첫 요청은 즉시 발송한다. 네트워크 Promise를 기다리는 대신 짧게 상태를 읽고 PC의 monotonic 시계로 6초 대기 한도를 확인한다. 끝난 요청과 중지된 실행은 정리한다. |
| 갱신된 목록에서 제거·잠금된 기존 회차를 다시 후보로 사용 | 미오픈 순환은 최신 공개 목록을 기준으로 후보를 다시 만든다. 사라진 기존 회차를 임의로 남기지 않고 날짜·극장도 대조한다. |

## 조회와 선점의 한도

- 좌석 탐색 중 별도 회차 GET은 최대 1개만 진행하고 조회 시작 간격 목표는 1초다. 아직 진행 중인 조회는 겹쳐서 시작하지 않는다.
- 진행 중인 가격/선점 요청은 중간에 끊지 않는다. 그동안 새 회차 결과 수집이나 다음 조회 시작은 늦어질 수 있다. 따라서 1초는 모든 조건에서 보장되는 발견 시간 상한이 아니다.
- 정상 응답 뒤에는 경과한 시간을 제외한 나머지만 기다리고 최소 50ms를 둔다. 통신 오류는 대기를 늘린다. 401·403·429나 감시 연결 유실을 확인하면 현재 순환의 추가 자동 선점을 중단한다.
- 실제 좌석 조회는 기존 350ms 최소 간격과 2초 요청 제한을 유지한다. 집계 0인 회차도 이 경로에서 한 번씩 확인하며, 좌석이 없으면 다음 시간으로 이동한다.
- 자동 추천은 시간대당 3개 조합 뒤 순환한다. 기본 `수동 좌석 우선`은 수동 후보 순서를 유지한다. 여러 시간대에 빠르게 기회를 주려면 `빠른 시간 순환 · 약 3초`를 선택한다. 진행 중인 거래 때문에 실제 전환에는 더 걸릴 수 있다.
- 가격 확인 후 선점 POST 순서는 유지하며 여러 선점을 동시에 제출하지 않는다. 확인된 선점의 화면 복구에는 기존 응답을 재사용한다.

## 재현 검증

최종 오프라인 검증 **637개 통과, 환경 의존 2개 제외**. 이번 버전 재현 테스트 41개를 포함한다.

순차 공개 시나리오: 11:00 회차만 먼저 존재하고 1초 뒤 14:30이 공개된다. 자동 추천 경합은 각 1초, 시간대당 3회이며 좌석 조회 지연은 없는 가상 조건이다.

| 버전 | 11:00 시도 시점 | 14:30 첫 시도 |
| --- | --- | --- |
| v6.80 | 0·1·2초, 다음 순환에서 3·4·5초 | 6초 |
| v6.81 | 0·1·2초 | 3초 |

이 비교는 회차를 다음 순환까지 미루던 제어 흐름의 개선이다. 서버 RTT나 실제 경쟁자의 제출 속도를 측정하지 않았다.

추가 테스트는 다음을 확인한다.

- 집계 0인 회차의 빈 좌석표에는 선점하지 않고, 실제 좌석이 가능해진 뒤 지정한 완전한 좌석 묶음으로 한 번만 진행.
- 잠긴 회차, 불완전한 ID, 다른 영화·포맷 거부. 최신 목록에서 사라진 회차와 다른 날짜 후보 제외.
- 시간 변경 기본 불허, 명시적 범위 안의 변경만 허용, 잘못된 값은 범위를 넓히지 않음. 예외 발생 후 실행별 설정 복원.
- 화면 준비·좌석 동기화·결제 연결 실패와 CDP 예외에도 일반 모드의 확인된 선점을 취소하거나 새 선점으로 넘어가지 않음.
- 실제 배포 JavaScript를 Node의 가짜 fetch로 실행. 모든 Chrome 타이머가 늦어지는 조건에서도 첫 GET 즉시 발송, 한 번만 발송, 401·403·429 전달, 취소 시 GET 정리.
- 네트워크 Promise가 끝나지 않는 조건에서 PC 시계로 대기 종료. 별도 회차 감시는 단일 요청만 유지하며 제한 응답 뒤 추가 선점을 중단.

검증 명령:

```bash
python -m pytest -q tests/test_cgv*.py tests/test_naver*.py tests/test_patch_notes.py tests/test_update_bootstrap.py -k 'not test_cgv_engine_enter_naver_pay_password_success and not test_cgv_npay_password_persistence_and_reservation_data'
```

기존 Windows 키패드 개인 이미지와 Windows 보안 저장소에 의존하는 테스트 2개는 Linux에서 실행 조건이 없어 제외한다. 이전 v6.79에서도 동일한 환경 실패를 재현했다. 이를 통과로 계산하지 않는다.

## 실사용 전에 알아둘 변화와 미검증 범위

1. 기존 저장 설정에 시간 변경 허용값이 없으면 **정확한 시간 일치**로 실행한다. 참고 날짜 시간표가 실제 날짜와 달라질 수 있고 그 차이를 허용하려면 CGV 선택창에서 범위를 명시적으로 정한 뒤 저장한다.
2. `임시선점 성공·화면 연결 미확인` 로그가 나오면 자동 예약이 완료된 것이 아니다. 확보 좌석을 자동 취소하지 않은 상태이므로 만료 전에 열린 CGV 화면과 예매내역을 확인해야 한다. 보존만으로 만료를 연장하지 않는다.
3. 서버 응답 자체가 유실된 선점의 본인 내역 자동 대조는 여전히 미구현이다. 검증된 CGV 임시선점 조회 계약이 없어 API를 추측해 추가하지 않았다. 성공 증거가 없으면 기존처럼 추가 제출 없이 멈춘다.
4. 브라우저 타이머와 네트워크 대기를 분리했지만, OS 절전·PC 종료·Chrome 프로세스 중단·CDP 연결 자체의 완전 정지까지 복구하는 보장은 없다. Windows에서 장시간 최소화/복원, 로그인 만료, 실제 개방 순간과 결제 연결은 별도 실환경 확인이 필요하다.
5. Windows GUI, 패치노트 버튼, EXE 빌드는 이 작업 환경에서 검증하지 않았다. 제공물은 **소스 PR과 Git 패치**이며, 설치 가능한 실행 파일이나 자동 업데이트 배포가 아니다.

Chrome의 [백그라운드 타이머 제한](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)과 [페이지 생명주기](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)는 브라우저 타이머만으로 대기 한도를 보장하지 않는 설계의 참고 자료다. Node 검증은 타이머 지연을 인위적으로 만든 재현이며 실제 Windows Chrome 최소화 시험을 대체하지 않는다.
