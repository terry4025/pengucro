# 단편선 v6.78 긴급 수정 및 통합 전달

기준 main: `1b19ca41fb8935eb43ce3f20e7d96343e18ebcd2` (v6.77).
네이버 v6.78 사용자 제공 패치를 함께 적용했다. 네이버 상세는 NAVER_V678_ANALYSIS.md.

## 변경

- 실제 DpsnnnSession.request 경로의 SharedReadGovernor를 호스트별 프로세스 내부 Condition/메모리 허가로 전환. 일반 HTTP 허가에서 SQLite 연결/트랜잭션/티켓/PID 검사가 없어졌다.
- 작업 슬라이더 1~32 유지. 프로세스별 실제 HTTP 동시 상한 32, 요청 시작 최소 간격 31.25ms(최대 약 32회/초). 여러 프로세스의 합산 한도는 공유하지 않는다.
- 상세/주문에 우선순위를 주되 연속 우선 허가는 최대 3회 이후 일반 요청에 기회를 준다. 우선 요청도 동시 상한/간격/backoff를 지킨다.
- 429/5xx/통신 실패에는 지수 대기, Retry-After 숫자/날짜 존중. Condition 대기와 중지 시 wake, 중지 폴백 확인 주기 최대 50ms. 진행 중 HTTP는 기존 네트워크 timeout까지 걸릴 수 있다.
- 응답 수신 후 정리 실패가 정상 주문 응답을 덮지 않도록 분리, 용량 반환은 멱등적. 네트워크 예외 시 POST 자동 재전송 없음.
- submission_lock, _order_claimed, 기존 OrderJournal 그대로 유지. 기록 삭제 없음. 서로 다른 목표는 각자 진행. 새로운 프로세스 간 중복 검사 없음.
- 내부 대기/실제 HTTP/전체 시간을 분리해 기록. 시작 시 작업별 추가 0.2초 누적 지연 제거(32번째 6.2초). 치명적 작업 오류는 명시 로그와 실행 중지; 정상 취소는 재시도 로그를 남기지 않는다.
- 실제 날짜/테마/시간 확인, 공개 슬롯만 주문, headless 준비 및 최종 접수 증거가 있는 완료 화면 표시 경로 유지. order_code만으로 성공 처리하지 않는다.

## 로컬 측정

Windows spawn, loopback HTTP/1.1, GET 응답 지연 30ms, 각각 12초. 4프로세스×32 비교에는 시작 4초 후 구 요청 DB 쓰기 잠금 3초 주입. 실사이트 호출/실예약/실결제 없음.

| 조건 | 오류/이탈 | HTTP 응답 수 | 허가 대기 p95/최대(ms) | 목표 최대 감시 공백(ms) | 공개→주문 최대(ms) | 중지 최대(ms) | DB 접근 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 이전 1×32 | 0/0 | 176 | 3217/3399 | 1666 | 66 | 135 | 7832 |
| 수정 1×32 | 0/0 | 369 | 1040/1042 | 63 | 35 | 16 | 0 |
| 이전 4×32 + DB 잠금 | 4/4 | 47 | 11815/12110 | 9910 | 2737 (2목표 주문 없음) | 152 | 10052 |
| 수정 4×32 + 구 DB 잠금 | 0/0 | 1467 | 1046/1058 | 72 | 31 | 28 | 0 |
| 수정 4×4 | 0/0 | 1492 | 98/130 | 66 | 26 | 30 | 0 |

수정 4×32와 4×4는 네 목표 각각 주문 1회. 측정된 동시 GET 피크는 각각 6/7(작업 수 128/16과 다름). 수정 4×32의 실제 HTTP p95 34ms, 전체 p95 1079ms. 개별 작업 대기 약 1초 동안에도 다른 작업이 같은 목표를 계속 감시한다.

4프로세스 전후에는 합산 이론 요청 예산도 약 32→128회/초로 늘어난다. 전체 처리량 개선을 모두 DB 제거 효과로 해석하면 안 된다. 동일 예산인 1프로세스 비교도 별도로 제시했다. 과거 15초 RTT는 순수 서버 시간이 아니다.

초기 HTTP/1.0 모의 서버는 Windows connection reset을 만들어 측정에서 제외했다. HTTP/1.1 재검증은 요청 오류 0. 종료 시 idle socket reset은 서버 측 정상 종료 처리로 구분한다.

재현: `tools/benchmark_dpsnnn_local.py --processes 4 --seconds 12 --hold 3 --output scratch/new-run.json`. `--baseline`은 기준 커밋 governor, `--workers 4`는 작업 수 비교. 출력 경로는 매번 새 이름. 원시 JSON은 로컬 scratch/keepalive-*.json에 있고 공개 커밋에는 넣지 않는다.

## 사용 권장 및 검증 한계

4개 창은 우선 각 병렬 4개를 권장한다. 이 로컬 조건에서는 32개보다 처리량이 낮지 않고 허가 대기/CPU 비용이 작았다. 실서버 최적값을 측정한 것은 아니므로 '4가 항상 가장 빠름' 또는 '32가 보장됨'으로 해석하지 말 것. 응답이 느리면 작업을 늘려도 429/backoff가 발생할 수 있다. 창 수 증가에 따른 외부 합산 요청량은 별도 관찰해야 한다.

모의 governor/HTTP spawn 검증과 실제 엔진의 미오픈→공개 슬롯→모의 완료, 동일 슬롯 중복 제출, 응답 유실/재시작 journal, 정리 실패 응답 보존, 429/503/중지 회귀 테스트를 각각 수행했다. spawn 부하 도구 자체는 GUI/실브라우저 결제 E2E가 아니라 요청 제어 측정이다. 실제 예약 경쟁 성공, 사이트 구조의 현재 실동작, 무제한 창 수, 긴 시간 감시는 보장하지 않는다.
