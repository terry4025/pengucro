- 실사이트의 캘린더 조회, 예약 가능 슬롯 선택, 상품 상세 진입, 비회원 임시 주문 생성과 결제 화면 진입은 확인했다.

- 이번 작업에서는 단편선 엔진 코드를 수정하지 않았다. 아래 항목은 후속 구현을 위한 우선순위다.

### 관측된 정상 예약 흐름

1. 예약 페이지가 `POST /booking/html_mfe_list.cm`으로 위젯을 준비한다.
2. `POST /booking/get_prod_list.cm`이 날짜별 상품과 예약 가능 상태를 반환한다.
3. 캘린더의 예약 가능 슬롯에서 `예약`을 누르면 `GET /reserve_g?idx=...&day=YYYYMMDD&endDay=YYYYMMDD` 형태의 상품 상세로 이동한다.
4. 상세 화면은 `POST /shop/load_booking_detail_day_calendar.cm` 및 `POST /shop/load_booking_detail_detail_calendar.cm`으로 주문 필드를 준비한다.
5. 비회원 예약을 진행하면 `POST /booking/add_order.cm`이 임시 주문을 만들고 `/shop_payment/?order_code=...` 결제 화면으로 이동한다.
6. 결제 화면에서 예약자 정보, 취소 규정, 결제 수단과 필수 동의를 입력한 뒤 `shop/check_payment.cm` 및 최종 결제 흐름이 이어진다.
7. 최종 성공은 단순 결제 URL이 아니라 예약번호 또는 확인 메시지로 판정해야 한다.

사이트는 직링과 날짜 수정 방식에서 낮은 확률의 중복 예약 오류가 발생한다고 공지하고 있다. 엔진이 정상 캘린더에서 받은 정확한 `idx/day`만 사용하도록 제한하고, 임의 날짜 조합이나 응답 유실 후 재제출을 금지해야 한다.

## 과거 예약 로그에서 확인한 문제

`app-20260813-27940.log`의 두 실행 모두 다음 순서를 보였다.

- 1차: 슬롯 포착 후 0.930초 만에 임시 주문 선점 성공, 약 8.097초 뒤 최종 결제 버튼 탐색 실패.
- 2차: 슬롯 포착 후 0.907초 만에 임시 주문 선점 성공, 약 6.497초 뒤 동일 실패.
- 두 실행 모두 시간표/상세/주문 생성 요청은 HTTP 200이었지만 최종 예약번호는 없다.

따라서 과거 문제의 중심은 슬롯 감시나 `add_order` 이전이 아니라 **결제 화면 이후의 자동 완결과 성공 증명**이었다.

## 현재 엔진의 문제점

### P0: 중복 주문과 오탐 성공 위험

1. `booking/add_order.cm` 응답이 타임아웃되거나 `order_code`가 보이지 않으면 짧은 대기 후 같은 mutation을 다시 보낸다. 서버가 주문을 생성한 뒤 응답만 유실한 경우 중복 주문이 가능하다 (`engines/dpsnnn_engine.py:468-501`, `1221-1248`).
2. `_checkout_success()`는 본문을 무시하고 URL에 `shop_payment_complete`가 포함되면 성공으로 본다. 예약번호 없이 5초가 지나도 성공을 반환하는 경로가 있다 (`738-746`, `985-999`).
3. `shop/check_payment.cm`은 명시적인 HTTP 성공과 `msg=SUCCESS`를 강제하지 않는다. 빈 응답이나 JSON 파싱 실패 뒤에도 최종 제출로 진행할 수 있다 (`928-942`).
4. 시작 중 재진입하면 `BaseEngine`의 실행 중 검사보다 먼저 `_order_claimed`를 초기화한다. 이미 선점한 실행의 잠금이 풀릴 수 있다 (`319-353`).

### P1: 미오픈 전환과 슬롯 선택 정확도

1. 같은 시간의 슬롯이 여러 개일 때 시간만 보고 첫 항목을 고른다. 첫 항목이 마감이고 두 번째가 가능하면 가능한 슬롯을 영원히 놓친다 (`1092`).
2. 마감 판정은 일부 class, `return false`, `완/마감` badge만 인식한다. 새로운 상태 문자열은 가용으로 잘못 판단할 수 있으므로 unknown 상태는 fail-closed로 처리해야 한다 (`118-152`).
3. worker 최초 예약 홈 GET은 반복 루프 밖에 있다. 일시적 타임아웃 한 번으로 해당 worker가 종료된다 (`1039-1050`, `1300-1305`).
4. 결제 화면에서 인원 필드 입력 함수의 반환값을 확인하지 않아 실제 입력 실패를 놓칠 수 있다 (`850-856`).

### P1: 요청량과 현재 브랜치 상태

1. 현재 코드는 세션 공통 rate governor, `Retry-After`, 429/5xx 지수 감속이 없다. 고정 40ms 반복은 장애 때 요청을 더 늘릴 수 있다.
2. 과거 `1cb1a93` 백업 브랜치에는 12세션 scan governor가 있었지만 현재 HEAD의 조상이 아니므로 현재 엔진에 포함되지 않는다.
3. 해당 백업도 6초 주기 주문 필드 사전 준비 요청은 governor 밖에 있어 그대로 복원하면 안 된다. 조회와 사전 준비를 하나의 전역 예산으로 묶어야 한다.

## 미오픈 날짜 검증 결과

- 현재 worker는 빈 슬롯 응답이면 계속 조회하고, 후속 응답에 목표 시간이 나타나면 주문 단계로 넘어간다.
- 인메모리 검증에서 `[] -> 열린 슬롯` 전환은 정상적으로 한 번만 주문 단계에 진입했다.
- 반대로 동일 시간에 `마감 slot_id=12`, `가능 slot_id=13`이 함께 있으면 현재 `next()` 선택은 12만 고르고 주문하지 못했다.
- 실제 자정 오픈 경계에서 새 MFE API와 레거시 `html_list.cm`이 같은 순간 같은 `idx/day`를 제공하는지는 아직 검증되지 않았다.

## 예약 사이트 분석기 개선 내용

- 아임웹의 읽기용 POST endpoint를 정확한 경로 allowlist로 분리하고 `add_order.cm`은 계속 차단했다.
- open Shadow DOM의 컨트롤, 폼, 달력과 상태를 재귀 탐색하도록 보완했다.
- Shadow DOM을 포함한 고유 selector와 화면 상태 서명을 생성한다.
- 숫자 날짜 대신 `aria-label`의 전체 날짜를 사용해 날짜 버튼을 페이징으로 오인하지 않게 했다.
- 같은 슬롯 위치가 `예약불가 -> 예약가능`으로 바뀌면 다시 평가한다.
- 예약 가능 카드의 짧은 `예약` 버튼은 상세 진입으로 허용하되 `예약하기`, `add_order`, 결제와 취소 mutation은 차단한다.
- fetch/XHR 응답 이벤트가 늦게 도착하는 경우 50ms 간격의 제한된 poll로 상태를 회수하고, 닫힌 probe page는 사이트 오류로 기록하지 않는다.

## 권장 구현 순서

1. `add_order`를 보낸 뒤 응답이 모호하면 재POST하지 말고 주문 조회/결제 페이지/예약 메시지로 reconciliation한다.
2. 성공 조건을 `2xx + 명시적 SUCCESS + 예약번호 또는 확인 메시지`로 강화하고 URL 단독 성공을 제거한다.
3. 목표 선택을 `time == target_time and available`로 바꾸고 unknown 상태를 차단한다.
4. 새 `get_prod_list.cm` 구조 데이터를 primary 또는 교차 검증 소스로 사용하고, 레거시 HTML은 fallback으로 둔다.
5. 초기 GET, 슬롯 조회, 상세 준비 요청 전체를 공통 rate governor와 backoff 아래 둔다.
6. 실제 테스트 슬롯에서 `미오픈 -> 자정 게시 -> 임시 주문 -> 최종 예약번호 -> 예약 취소 완료`를 한 번의 추적 ID로 검증한다.

## 후속 완료 기준

- 응답 유실을 주입해도 `add_order`가 두 번 전송되지 않는다.
- 동일 시간 중 마감/가능 항목이 섞여도 가능한 항목을 선택한다.
- 미오픈 날짜가 열린 직후 정확한 날짜와 slot ID만 사용한다.
- 429/5xx/timeout에서 모든 worker가 공통 감속하고 회복한다.
- 최종 성공에는 예약번호 또는 단편선의 확정 응답이 필요하다.
- 실예약 테스트의 취소 완료 화면 또는 취소 상태까지 확인한다.
