# 네이버 선결제 실패 로그 분석 및 v6.78 패치

## 결론

첨부된 실패 실행은 네이버의 `RT47 / OUT_OF_STOCK` 응답을 받았으며, 후속 조회에서 재고 0/1, 본인 예약내역 미확인으로 종료했다. 크롬 타이머 발사 오차는 +0.0ms였고, 신버전도 네이버 `currentDateTime`을 조회했다. 따라서 **“네이버 서버 시각을 버리고 PC 시계만 사용해서 실패했다”는 설명은 로그·코드와 맞지 않는다.**

다만 타이머가 정확하게 발사되는 것과 오픈 시각을 정확하게 계산하는 것은 별개다. 오픈 직전에 별도 시각 추정으로 기준을 바꾸는 경로, 불확실성 축소 표시, 구버전 학습값 이관, 타이머 준비 실패 시 처리에서 수정할 결함을 확인했다. 이 결함의 수정은 검증했지만, 첨부 두 실행의 승패를 특정 결함 하나로 확정하거나 실서버 예약 성공을 보장하지 않는다.

최종 적용 기준: GitHub main v6.77, `1b19ca41fb8935eb43ce3f20e7d96343e18ebcd2`. 분석은 v6.76에서 시작했으나 작업 중 main에 단편선 v6.77이 반영되어 해당 변경을 보존한 v6.78로 통합했다. 최신 단편선 개선 위에 네이버 수정만 추가한다. 로그에 실행 버전이 없으므로 ‘구버전/신버전’을 정확한 릴리스 번호에 대응시키지는 않았다.

## 첨부 로그 비교

원본: `구버전 바야흐로 성공.log`, `신버전 바야흐로 실패.log`. 아래 시각은 로그에 기록된 PC 시각이다. 서버 자정과 PC 자정은 약 4초 차이가 난다.

| 항목 | 구버전 성공 로그 | 신버전 실패 로그 |
|---|---|---|
| 대상 | 9월 11일 20:45 | 9월 11일 19:10 |
| 테스트 모드 | Npay 최종 결제 전 중지 | 동일 |
| 초기 서버 시각 보정 | PC 대비 +4.30초 | PC 대비 +4.25초 |
| 오픈 직전 조회 제한 | 23:59:48.731 TooManyRequests | 23:59:48.886 TooManyRequests |
| 제출 경로 | Python에서 브라우저 API 제출 호출 | 브라우저 내부 예약 타이머 |
| 제출/응답 | 23:59:55.651 전송, 56.075 성공 | 23:59:56.720 refused 응답 로그 |
| 왕복 시간 | 424ms | 273ms |
| 표시된 발사 시점 | 추정 오픈 -49ms | 추정 오픈 -121.9ms |
| 표시된 서버 도착 | 기록 없음 | 추정 -70ms, 실제 서버 계측값 아님 |
| 브라우저 시각 추정 | 해당 로그 없음 | 5회, 최저 RTT 104ms, 추정 불확실성 ±243ms |
| 결과 | 임시 선점 후 Npay 본인인증 대기 | RT47 / OUT_OF_STOCK, 재고 0/1, 예약내역 미확인 |

구버전의 ‘성공’은 **임시 자리 선점 성공**이다. 결제 완료·최종 예약 확정 성공 로그는 없다. 시간대가 다른 두 실행이므로 경쟁 상황을 통제한 A/B 비교도 아니다. 여러 PID와 크롬 포트 충돌은 동시 실행 흔적이며, 양쪽의 조회 제한은 요청량을 줄일 이유지만 예약 실패의 단독 원인이라는 증거는 아니다.

실패 로그에서 Python의 ‘오픈 4834ms 전’은 PC 시각 약 23:59:55.891을 오픈으로 가리킨다. 이후 브라우저는 별도 5회 표본으로 기준을 바꾼다. 응답 기록 시각에서 RTT를 빼면 23:59:56.447이지만, Python의 결과 읽기·로그 지연이 포함되므로 이를 실제 발사 시각으로 단정할 수 없다. 원시 시각 표본과 서버 수신 시각이 없어 정확한 기준 이동량은 복원할 수 없다.

## 확인한 코드 결함과 수정

1. **오픈 직전 시각 기준 교체와 추가 조회**
   - 기존: 이미 동기화한 NaverServerClock과 별개로 Chrome에서 5회 서버 조회 후 새 오픈 시각을 채택했다. 기존 기준과 차이를 검증하지 않았다. 전체 조회가 실패하면 조회에 소요된 시간 뒤에 상대 대기 시간을 다시 적용할 수도 있었다.
   - 수정: NaverServerClock의 오픈 마감 시점을 단조 시계로 고정한다. 로컬 CDP 시계 읽기 3회 중 가장 짧은 왕복 표본으로 Chrome performance 시계에 전달한다. 오픈 직전 서버 조회 5회를 제거하고, 준비 시간·PC 시계 변경이 마감 시점을 뒤로 밀지 않게 한다. 페이지 이동으로 시계 기준이 바뀌면 설치하지 않는다.
   - 기존 서버 응답 완료 시점 앵커와 전송 지연 추정 방식은 유지했다. 서버 내부 처리·비대칭 네트워크 지연은 여전히 직접 계측할 수 없다.

2. **실제보다 작게 표시되는 정밀도**
   - 기존 Python 시계는 `min(RTT/2, 25ms)`로 불확실성을 최대 25ms로 잘랐다. 브라우저의 표본 분산도 실제 서버 도착 오차의 보장된 상한처럼 표시했다.
   - 수정: RTT와 표본 간 차이를 반영하고 25ms 상한을 제거했다. 표시를 ‘표본 기준 불확실성’으로 바꾸고, 실제 도착 오차의 상한을 보장하지 않음을 구분했다.

3. **구버전 조기 제출 학습값의 재활성화**
   - 기존: 한 상품을 기록할 때 전체 파일 버전을 v2로 바꾸면서 다른 상품의 v1 선결제 학습값은 그대로 둘 수 있었다. 다음 로드에서 그 값이 정상 v2 값으로 인정됐다.
   - 수정: 버전 전환 전에 모든 선결제 상품을 이관한다. 이미 v2로 잘못 표시된 선결제 값도 기존 안전 기본값 20ms를 초과해 적용하지 않는다. 명시적 미오픈에 의한 10ms 조정은 유지한다. 수동으로 학습 파일을 삭제할 필요가 없다.
   - 실패 로그의 70ms 값이 이 버그에서 유래했는지는 원본 학습 파일과 실행 버전이 없어 확정할 수 없다. 현행 v6.76의 신규 선결제 기본값은 이미 20ms다.

4. **타이머 설치 응답 유실과 조기 대체 제출**
   - 기존: Python의 타이머 준비 오류를 실제 타이머 미설치로 간주하고 바로 직접 제출할 수 있었다. Chrome 타이머가 이미 설치됐거나 뒤늦게 설치되면 중복 제출 위험이 있었다. 정상적인 대체 경로에서도 오픈 전에 너무 일찍 보낼 수 있었다.
   - 수정: 해당 타이머의 취소가 명확하게 확인돼야 직접 제출로 전환한다. 상태가 불명확하면 추가 제출 없이 예약내역을 대조한다. 안전한 대체 제출도 예정 전송 시점까지 기다린다. 타이머를 설치할 여유가 부족한 경우에도 같은 대기를 적용한다.
   - 첨부 실패 실행에서는 설치 오류가 기록되지 않았으므로, 이는 추가로 발견한 결함이다.

5. **준비된 미오픈 슬롯 반복 조회**
   - 예약 가능 슬롯이 확인됐지만 아직 오픈 전인 대기는 최소 1초 간격으로 완화한다. 오픈 5초 전 준비 시점에는 맞춰 깨어나며, 실제 제출을 1초 간격으로 하는 변경이 아니다. 미공개 슬롯 탐색·오픈 이후 감시와 명시적 미오픈 재시도는 기존 경로를 유지한다.
   - 다음 로그부터 시작 시점에 버전과 릴리스 순서를 기록한다.

## 검증과 한계

- 네이버 API·제출·엔진·학습·폼·시계 전달·패치노트: **244개 통과**.
- 앱 시작·업데이트 연동: **16개 통과**. 합계 **260개 통과**.
- 실제 배포용 JavaScript를 Node의 가상 시계/가짜 fetch로 실행했다. 성공·RT47·불명확 응답은 제출 1회, 명시적 미오픈만 재시도, 취소·페이지 변경은 제출 0회를 검증했다.
- 준비 지연·PC 시각 변화에 대한 마감 시점 유지, 설치 응답 유실과 취소 확인, 잘못 이관된 학습값, 대체 제출의 대기도 회귀 검증했다.
- 실제 네이버 예약 생성·결제는 하지 않았다. 이는 오프라인 회귀 검증이며 실서버 선점 성공률 시험이 아니다.
- 현재 환경은 Linux다. Windows 전용 `winsound`가 필요한 UI 경로는 실행할 수 없어 단편선 UI 라우팅 테스트 수집이 중단됐다. 네이버 검증은 별도 실행해 통과했다. Windows EXE 빌드, 패치노트 버튼 실동작, Npay 인증·최종 결제는 미검증이다.

## 적용 및 Windows 빌드

`pengucro-v6.78-naver.patch`는 위의 v6.77 기준 커밋에 적용하는 Git 메일 패치다. 원본 로그·연락처·인증 정보는 포함하지 않는다.

```powershell
# 작업 내용이 커밋되거나 보관된 v6.77 소스에서 실행
 git switch -c fix/naver-prepay-v678
 git am --3way C:\path\pengucro-v6.78-naver.patch
```

적용 후 `pengucro/__init__.py`의 버전 6.78, 순서 6780001을 확인한다. `docs/AUTO_UPDATE_RELEASE.md`의 Windows 환경에서 테스트, `verify_ui.py`, `build_run.py`와 EXE 점검을 진행해야 한다. 이 패치 파일 자체는 실행 파일이나 자동 업데이트 배포 완료본이 아니다. `AGENTS.md`에 따라 빌드는 커밋된 깨끗한 소스에서 수행하고, 변경이 생기면 새 커밋으로 다시 빌드한다. 서명 키를 패치에 넣지 않는다.

다음 실사용 비교에는 앱 시작부터 종료까지의 로그와 실제 목표 슬롯을 함께 남긴다. 구·신 버전을 같은 환경에서 동시에 실행하면 요청량·크롬 세션·경쟁 조건이 섞이므로 성공률 비교 근거로 부적절하다. 임시 선점과 최종 결제 완료를 별도로 확인한다. RT47 이후에는 수동 재시도 전에 본인 예약내역을 확인한다.
