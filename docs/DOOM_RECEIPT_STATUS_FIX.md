# 둠이스케이프 환불 상태 성공 오판 수정

기준: v6.78 배포 소스 70adb81. 소스 수정이며 새 EXE 빌드/배포는 포함하지 않음.

확인한 결함: 이전 단계 meta refresh 주소와 최종 HTML을 합쳐 `완료` 또는
`rev.make.exe.php` 등 문자열만으로 성공 처리했다. 실제 최종 페이지가 환불이어도
성공 callback이 발생하는 것을 로컬 모의 응답으로 재현했다. 첨부 실행에서 환불로
전환된 원인/시점이나 문자 미발송 원인은 서버 이력 없이 확정할 수 없다.

## 변경

- 일반 비동기/동기 경로와 이미 완료된 주문 복구 경로 모두 기존 주문의 완료 페이지를 읽어 확인.
- HTTP 2xx, 표시된 예약번호, 예약자/상태 필드의 정상 상태, 목표 날짜·테마·시간이 모두 필요.
- ck_code와 완료 페이지 링크는 접근에만 사용하며 예약번호·성공 증거로 사용하지 않음.
- 환불/취소, 다른 목표, 로그인 페이지, 번호 누락, 네트워크 오류는 성공 차단.
- 비동기 확인은 같은 주문 GET만 최대 3회. 확정 요청/주문을 다시 전송하지 않음.
- 불명확한 결과를 '선점 성공'으로 표시하던 fallback 제거. 상태 확인 필요로 정지.
- 환불 규정 문단이나 script의 글자는 예약 상태로 취급하지 않음.
- 이름/연락처/접근코드를 제외한 상태·목표 일치·예약번호 표시 여부만 진단.
- 사전 준비 캐시 사용 여부와 슬롯 발견→POST 준비 시간 로그 추가.

주문 생성 이전의 요청 수/감시 속도/가격 캐시 정책은 바꾸지 않았다. 검증 GET은
주문 이후에만 실행하므로 선점 전 경로를 늘리지 않는다. 속도 향상을 실측했다고
주장하지 않는다. 추가 GET 때문에 성공 알림까지는 더 걸릴 수 있다.

## 검증 및 한계

환불/취소 최종 페이지로 실제 모의 worker를 실행했을 때 주문 POST 1회, 성공 알림
0회를 확인했다. 정상 신청은 성공 1회. 상태/목표 불일치, 500, 확인 재조회,
동기 timeout, 개인정보 비노출도 검증한다.

실예약/결제는 실행하지 않았다. 현재 전체 실제 예약 상세 HTML은 제공되지 않아
라벨 구조는 모의 HTML과 첨부 화면에 기반한다. 실제 화면이 예상 라벨과 다르면
성공으로 추측하지 않고 확인 필요로 정지한다. 다음 검증에는 정상/환불 상세 화면의
개인정보 제거 HTML을 확보해 파서 호환성을 확인해야 한다. 성공 판정 이후 나중에
사이트가 예약 상태를 변경하는 것을 지속 감시하는 기능은 이번 수정에 포함하지 않았다.
