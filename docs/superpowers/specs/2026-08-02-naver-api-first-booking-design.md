# 네이버 API-first 예약 선점 설계

## 목표

네이버 예약 오픈 순간의 React 시간표 렌더링과 화면 클릭 왕복을 제거하고,
이미 로그인된 Playwright 브라우저 세션에서 `submitBooking` GraphQL mutation을
직접 호출한다. 정상 준비 상태에서는 오픈 후 첫 예약 요청을 한 번의 네트워크
왕복으로 끝내며, 직접 제출을 신뢰할 수 없는 상태에서는 기존 브라우저 제출로
안전하게 전환한다.

성공 기준은 다음과 같다.

- 오픈 전 로그인, CSRF, 사업장, 상품, 슬롯, 사용자 입력을 검증하고 제출
  페이로드를 완성한다.
- API 준비가 완료된 실행은 오픈 순간에 페이지를 새로고침하지 않는다.
- 성공 응답의 `bookingId`를 실제 예약 성공으로 기록한다.
- `BizItem is not opened.`만 제한적으로 재시도한다.
- 인증, 페이로드, 네트워크 및 `RT98` 오류는 API 재시도를 중단하고 브라우저
  방식으로 전환한다.
- 개발자 테스트 모드에서는 어떤 예약 mutation도 서버로 보내지 않는다.
- 쿠키, CSRF 토큰 및 전체 제출 페이로드를 로그나 평문 파일에 남기지 않는다.

## 선택한 접근

### Playwright 페이지 컨텍스트의 직접 GraphQL 호출

예약 요청은 Python `requests` 세션이 아니라 이미 로그인된
`m.booking.naver.com` 페이지의 `fetch()`로 전송한다. 이 방식은 브라우저의
쿠키, User-Agent, Origin 및 동일 출처 세션 문맥을 그대로 사용하면서 React
렌더링만 건너뛴다. 별도의 쿠키 복사 과정에서 발생할 수 있는 도메인 중복,
세션 불일치 및 브라우저와 다른 요청 지문을 피할 수 있다.

Python `requests` 기반 `submit_booking()`은 서버 응답 분류와 진단용 저수준
클라이언트로 남기되, 운영 예약의 기본 전송 경로로 사용하지 않는다.

## 구성 요소

### 1. 제출 페이로드 모델 및 빌더

`engines/naver_submit.py`를 추가해 브라우저 제어와 분리한다.

- `NaverSubmitPreparation`: 제출 가능 여부, 완성된 입력, 실패 사유를 담는다.
- `NaverSubmitPayloadBuilder`: business, bizItem, 전체 slot 레코드, account,
  사용자 예약 데이터를 `SubmitBookingParams`로 변환한다.
- `validate_submit_payload()`: ID, slot 시간, CSRF, custom form, 예약 인원 및
  즉시확정/비결제 상품 조건을 검증한다.

현재 최소 조회용 `hourlySchedule` 쿼리는 제출에 필요한 슬롯 이름, 종료 시각,
가격 및 옵션 필드를 포함하는 별도 상세 쿼리로 확장한다. 사업장과 상품 쿼리도
네이버 페이지가 실제 mutation에 넣는 필드만 요청한다. 원본 GraphQL JSON 값은
불필요하게 재해석하지 않고 서버가 반환한 형태를 보존한다.

첫 지원 범위는 현재 확인된 일반 EPISODE형, 좌석 미사용, 기간 고정 아님,
네이버페이 즉시결제 미사용 상품이다. 좌석, 기간제, 필수 결제 상품은 잘못된
페이로드를 보내지 않고 API 준비 실패로 처리해 브라우저 방식으로 전환한다.

### 2. 브라우저 계정 및 전송기

`NaverEngine`이 상품 페이지를 열고 로그인을 확인한 뒤 페이지 컨텍스트에서
`account` GraphQL 쿼리를 실행해 `isLoggedIn`, `csrfToken`, `isSmsAlarm`을
얻는다.

`NaverBrowserSubmitter`는 다음 인터페이스를 제공한다.

- `prepare(...) -> NaverSubmitPreparation`
- `submit(prepared_input) -> SubmitResult`

`submit()`은 페이지 컨텍스트의 `fetch("/graphql", {credentials: "include"})`를
한 번 실행하고 GraphQL의 `data` 또는 `errors[0].extensions`를 기존
`SubmitOutcome`으로 변환한다. 입력 전문과 인증 값은 예외 메시지에도 포함하지
않는다.

### 3. 엔진 통합

브라우저 로그인 완료 직후 API 제출 준비를 수행한다. 준비 성공 시
`API 직접 제출 준비 완료`를 기록하고, 실패 시 정확한 비밀정보 없는 이유와
`브라우저 제출로 전환`을 기록한다.

오픈 시각이 공개된 상품의 전용 strike는 다음 순서로 동작한다.

1. 오픈 직전 서버 시계를 다시 동기화한다.
2. 최근 정상 API RTT의 절반을 제한된 편도 지연 추정치로 사용한다.
3. 요청이 서버에 오픈 시각 부근에 도착하도록 전송 시작 시각을 계산한다.
4. 준비된 페이로드를 페이지 새로고침 없이 제출한다.
5. `NOT_OPEN`일 때만 총 3회, 350ms 이내에서 재시도한다.
6. 성공이면 `bookingId`를 기록하고 실행을 종료한다.
7. 정원 마감/중복이면 실패 원인을 기록하고 취소표 감시를 계속한다.
8. 인증, 페이로드, RT98 또는 불명확한 오류이면 그 실행의 API 경로를 비활성화하고
   기존 브라우저 제출로 전환한다.

오픈 시간이 없고 취소표를 감시하는 상품도 슬롯이 예약 가능으로 바뀌면 준비된
API 요청을 먼저 사용한다. API 경로가 비활성화된 경우에만 현재 `_submit()` 화면
흐름을 사용한다.

### 4. 개발자 테스트 모드

개발자 테스트 모드에서는 `submit()`을 호출하지 않는다. 완성된 페이로드를
검증한 뒤 다음 정보만 로그로 보여준다.

- API 준비 성공/실패
- 상품, 슬롯 ID 및 예약 시각
- 포함된 최상위 필드 이름
- 누락되거나 지원하지 않는 조건

CSRF, 쿠키, 사용자 개인정보 및 각 필드의 실제 값은 출력하지 않는다.

정확한 페이지 페이로드를 비교해야 할 때 사용할 캡처 도구는
`submitBooking` 요청을 Playwright route에서 가로채 JSON을 메모리에서
정규화한 뒤 반드시 `abort()`한다. 이 도구는 테스트/개발자 모드에서만 활성화되며
원격 서버로 mutation을 전달하지 않는다.

## 오류 처리

| 결과 | 처리 |
| --- | --- |
| `SUCCESS` | 예약번호 기록, 성공 알림, 실행 종료 |
| `NOT_OPEN` | 제한 시간과 횟수 안에서만 재시도 |
| `REFUSED` | 정원 마감/중복 기록, 취소표 감시 계속 |
| `AUTH` | API 비활성화, 로그인 확인 후 브라우저 제출 |
| `PAYLOAD` | API 비활성화, 필드 이름만 진단 로그, 브라우저 제출 |
| `ABUSE` (`RT98`) | API 즉시 비활성화, 경고, 브라우저 제출 |
| `ERROR` | API 비활성화, 네트워크 요약 로그, 브라우저 제출 |

Mutation은 일반 가용성 폴링처럼 반복하지 않는다. `NOT_OPEN` 이외 결과에는
추가 mutation을 보내지 않아 계정 제한 위험을 줄인다.

## 시각 동기화

기존 5분 주기 동기화는 유지하되 오픈 5초 전 추가 동기화를 수행한다. 여러 번
측정할 경우 RTT가 가장 짧은 정상 표본을 채택한다. 편도 지연 보정은 최근 RTT의
절반을 사용하되 10~100ms 범위로 제한한다. 로컬 이벤트 루프 지연과 실제 네트워크
편차는 각 로그에 `전송 시작`, `응답 수신`, `서버 오픈 대비 오프셋`, `RTT`로
남기되 인증 데이터는 기록하지 않는다.

## 테스트 전략

### 단위 테스트

- 캡처 후 비식별화한 실제 요청 fixture와 빌더 결과의 필드 구조를 비교한다.
- 필수 필드, custom form, 시간 및 지원 상품 조건 검증을 테스트한다.
- 각 GraphQL 오류를 `SubmitOutcome`으로 분류한다.
- 로그와 예외에 쿠키, CSRF, 이름 및 전화번호가 포함되지 않는지 확인한다.

### 엔진 테스트

- API 준비 성공 시 오픈 strike가 `_goto_item()`과 화면 `_submit()`을 호출하지
  않고 직접 제출을 한 번 수행하는지 확인한다.
- `NOT_OPEN`만 제한적으로 재시도하는지 확인한다.
- `AUTH`, `PAYLOAD`, `ABUSE`, `ERROR`가 API를 비활성화하고 브라우저 경로로
  전환하는지 확인한다.
- `REFUSED`는 취소표 감시를 계속하고 mutation을 반복하지 않는지 확인한다.
- 개발자 테스트 모드에서는 전송 함수가 한 번도 호출되지 않는지 확인한다.

### 라이브 비파괴 검증

- 공개 조회 쿼리와 무로그인 mutation의 인증 거절까지만 자동 확인한다.
- 로그인된 페이로드 검증은 먼저 route abort 캡처로 수행한다.
- 사용자의 별도 승인 없이는 예약 가능한 슬롯에 mutation을 보내지 않는다.
- 로그인된 실서버 거절 검증이 필요하면 이미 마감된 슬롯만 사용하며, RT98 위험을
  사용자에게 알리고 별도 승인을 받은 뒤 1회만 실행한다.

## 관측 가능성

로그는 예약 경쟁 구간을 다음 단계로 구분한다.

- `API 준비`
- `오픈 대기`
- `직접 제출 전송`
- `응답 수신`
- `직접 제출 비활성화`
- `브라우저 폴백`

사용자에게는 “조회만 API인지”, “직접 제출까지 API인지”가 항상 명시되어야 한다.
준비되지 않은 실행을 API 방식으로 표시하지 않는다.

## 범위 밖

- 네이버의 RT98 판정 우회
- 캡차 또는 본인인증 우회
- 좌석 선택, 기간제, 필수 선결제 상품의 직접 제출
- 여러 계정이나 여러 탭을 이용한 동시 중복 요청
- 예약 성공 보장 문구

이 설계는 렌더링 지연을 제거하고 첫 요청 시점을 앞당기지만, 네트워크 상태,
서버 경쟁 및 네이버 정책 때문에 예약 성공 자체를 보장하지는 않는다.
